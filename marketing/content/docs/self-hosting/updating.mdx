title: Updating
description: Upgrade a running TraderMemos instance — pull, restart, done. Migrations run automatically.
---

Database migrations run **automatically on API startup** — upgrading is pull + restart.
Still, [back up](/en/docs/self-hosting/backup-restore) before major version jumps.

## Docker (default)

```bash
cd TraderMemos
git pull                     # picks up compose/Makefile changes, if any
docker compose pull          # fetch newer images
make up                      # recreate containers (docker compose up -d)
```

If you built from source instead of pulling Hub images:

```bash
git pull
make up-build                # rebuild both images from the repo
```

Verify the running version:

```bash
curl -s http://localhost:3000/healthz
# {"status":"ok","version":"0.15.0","go":"go1.27.0","commit":"…"}
```

## Pinning versions (recommended for production)

`latest` moves with every release. Pin a release in the root `.env` and bump deliberately:

```bash
# .env
TM_IMAGE_TAG=0.15.0
```

```bash
# upgrade: edit TM_IMAGE_TAG, then
docker compose pull && make up
```

Published tags follow semver: `0.15.0`, `0.15`, `0`, `latest`, plus immutable commit-`sha` tags.
Images are multi-arch (`amd64` + `arm64`). Releases and notable changes are listed in the
[CHANGELOG](https://github.com/sinhong2011/TraderMemos/blob/main/CHANGELOG.md) and
[GitHub Releases](https://github.com/sinhong2011/TraderMemos/releases).

## How migrations behave

- Migrations are embedded in the API binary and applied on boot (SQLite and Postgres chains).
- A file lock next to the SQLite DB (`tradermemos.db.migrate.lock`) prevents concurrent
  migration if two processes start at once.
- There is **no automatic downgrade**. Rolling back to an older image after a schema migration
  is not supported — restore the [pre-upgrade backup](/en/docs/self-hosting/backup-restore)
  instead.

## Custom trading-system schema (one-time)

A draft trading-system map build applied its SQLite migrations as versions 50–52
(Postgres 14–16) before official 0.16.1 published `mcp_settings` as SQLite 50 /
Postgres 14. Official 0.16.1 then refused to start on those databases
(`no migration found for version 52`).

Current official numbering is:

- SQLite 50 `mcp_settings`, 51 `trading_system`, 52 `system_plans`, 53 `system_plan_evidence`
- Postgres 14 `mcp_settings`, 15–17 the same feature chain

On startup, if the API finds trading-system tables already present, `mcp_settings`
missing, and `schema_migrations` still at the old custom version (SQLite 50–52 or
Postgres 14–16), it applies `mcp_settings` and records the matching official
version from the tables that already exist, then runs any remaining migrations.
Existing trading-system, plan, evidence, and weekly-review rows are left in place.
MCP stays off until the owner opts in. A [pre-upgrade backup](/en/docs/self-hosting/backup-restore)
is still required.

If `schema_migrations` reports one of those versions but the database matches
neither the custom history nor the official chain, startup stops with an error
rather than rewriting the version.

## Fork / CDN deployments

- **Vercel / Cloudflare / Netlify web**: pushes to your fork's default branch redeploy
  automatically; syncing your fork with upstream *is* the update.
- **Railway API**: redeploys on push. The `/data` volume persists across deploys — keep it
  attached.
